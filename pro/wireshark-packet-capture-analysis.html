What This Project Is About

A PCAP is a saved record of network traffic. It lets an analyst review who talked to whom, which ports were used, which protocols appeared, and what behavior patterns stood out during the capture window.

This project trains practical packet analysis instead of theoretical memorization. The main skill is learning how to ask good investigation questions and prove answers from packet evidence.

Working principle: Treat packets as evidence. A filter helps narrow the view, but the conclusion comes from repeated behavior, timestamps, source and destination context, protocol details, and clearly documented limits.

Who This Is For

This note is for learners who already understand basic networking and want to practice analysis in a more professional way. You do not need to be an expert, but the following foundations should already feel familiar.

Addressing and ports IP addresses, source and destination traffic, service ports, and the difference between clients and servers.
Network models TCP/IP model thinking, OSI model basics, and how layers help during troubleshooting.
Common protocols TCP, UDP, DNS, HTTP, HTTPS/TLS, ICMP, and ARP at a beginner-friendly practical level.
Suspicious patterns Scanning, brute force attempts, beaconing, exfiltration, denial of service, and cleartext service exposure.

Wireshark Interface Basics

This is a short orientation, not a full beginner lesson. The useful habit is knowing which pane answers the current analysis question.

Packet List Pane The timeline of captured packets. Use it to see frame number, time, source, destination, protocol, length, and the short summary.
Packet Details Pane The decoded structure of the selected packet. Expand protocol layers here to inspect headers, flags, fields, and values.
Packet Bytes Pane The raw bytes behind the selected packet. It is useful when payload text, protocol fields, or exact byte evidence matters.
Display Filter Bar The investigation search box. It hides or shows packets after the capture is loaded, which makes it safer for learning.
Toolbar and Menus Shortcuts for opening captures, navigating packets, managing views, and finding protocol statistics.
Status Bar Quick feedback about capture state, packet counts, profile, and whether the current filter is valid.

Beginner Workflow

The first goal is not to find every interesting packet. The first goal is to learn a repeatable path that turns an unknown capture into a small set of defensible observations.

Practice capture for this workflow

Use this exact PCAP when following the beginner workflow:

https://github.com/UnExplainableFish52/wireshark/blob/main/pcaps/net_ctf.pcapng
1. Open Wireshark Start with a clean view and avoid applying filters before you know what is in the file.
2. Load the practice capture Open pcaps/net_ctf.pcapng and let the full packet list load.
3. Check capture properties Note the file type, packet count, duration, time format, and any capture comments or metadata.
4. Review protocol hierarchy Identify which protocols dominate and whether anything appears unexpectedly often.
5. Review conversations Look for top talkers, repeated connections, unusual service ports, and one-sided traffic.
6. Filter on a host Use ip.addr == <host-ip> to isolate traffic involving one host without destroying evidence.
7. Answer guided questions Work through the practice questions and write down the filter or view used for each answer.
8. Separate facts from guesses Facts come from packets. Guesses are allowed in notes, but they must be labeled as interpretations or unknowns.

First Filters To Learn

Good filters are small and question-driven. Start broad, observe the result, then narrow only when the question becomes more specific.

Filter What it shows Question it helps answer
ip All IPv4 traffic in the capture. Which packets are IP-based traffic?
tcp All TCP traffic, including connection setup and application sessions. Which hosts are trying to establish reliable connections?
dns DNS queries and responses. Which names were looked up, and did responses succeed or fail?
ip.addr == <host-ip> Traffic where the selected host is either source or destination. What did this host send or receive during the capture?
tcp.flags.syn == 1 && tcp.flags.ack == 0 Initial TCP SYN attempts without SYN/ACK. Is a host initiating many connection attempts, possibly scanning or probing?

Filter Thinking Guide

Display filters and capture filters are not the same. Display filters are used after a capture is loaded and only hide or show packets. Capture filters are used before or during capture and affect what gets saved.

For learning, display filters are safer because they do not remove evidence from the file. A filter should answer a question, not simply make the screen look cleaner.

ip.addr == 10.0.0.5 Show all traffic involving one host, whether it sent or received the packet.
ip.src == 10.0.0.5 Show packets sent by one host.
ip.dst == 10.0.0.5 Show packets received by one host.
dns.flags.response == 1 and dns.flags.rcode != 0 Find DNS responses that returned an error code.
http.user_agent matches "(?i)(python|curl|wget|nmap|masscan|zgrab|nuclei)" Look for HTTP clients that may indicate scripts, scanners, or automated probes.
tls.handshake.type == 1 and tls.handshake.extensions_server_name Show TLS Client Hello packets that include server name information.
Discipline: A matching filter is not the same as a finding. It is a starting point for review, comparison, and evidence collection.

Practical Analyst Method

A SOC-style workflow keeps the analysis from becoming random clicking. Move from context to overview, then to hosts, protocols, attack patterns, evidence, and reporting.

Before analysis, ask

  • What is the context of the capture?
  • What do we suspect happened?
  • What is the time window?
Phase 1: Get the big picture Capture duration, total packets, average packet size, file type, timestamp format, expert information, and protocol hierarchy.
Phase 2: Map the network Internal and external IPs, top talkers, conversations, exposed services, and unusual one-way traffic.
Phase 3: Analyze protocols DNS, TCP, HTTP, TLS, SMB, and Windows services, with each protocol reviewed for behavior and evidence.
Phase 4: Recognize attacks Port scanning, brute force attempts, beaconing, exfiltration, and suspicious cleartext protocol usage.
Phase 5: Collect evidence Filters used, timestamps, source and destination, protocol and port, packet or frame references, and confidence level.
Phase 6: Write a report Summary, scope, key findings, evidence, limitations, and recommendations.

Useful Wireshark analyst views

After the first pass, the stronger work comes from cross-checking packet behavior with Wireshark's built-in analysis views instead of relying on one filtered packet list.

Capture File Properties Confirm the capture window, packet count, file metadata, and timestamp assumptions before making a timeline claim.
Protocol Hierarchy Identify protocol mix and high-volume protocol families before drilling into individual packets.
Endpoints and Conversations Find top talkers, repeated client-server pairs, one-sided attempts, and high-volume relationships.
Follow TCP Stream Reconstruct cleartext sessions carefully when payload is visible, while avoiding claims beyond the stream evidence.
Expert Information Use warnings and notes as leads, then verify the relevant packets manually before reporting.
IO Graphs and Time Windows Spot bursts, scanning waves, traffic spikes, and quiet periods that help structure a timeline.

Analyst Judgment

PCAP evidence can show what happened on the network, but it cannot always prove the full story. Good analysis keeps facts, interpretations, assumptions, and unknowns separate.

PCAP can show Network conversations, protocol behavior, visible payloads, service banners, timing, ports, and repeated traffic patterns.
PCAP cannot always prove User intent, endpoint process names, shell history, prior compromise, or post-capture activity. Authorization status cannot be determined from PCAP alone.
Reports should separate Facts from packets, analyst interpretation, assumptions made for context, and unknowns that require more data.

Security Lessons Learned

The project is most useful when the packet analysis becomes general security judgment. These are the lessons that carry into SOC work, incident notes, and defensive reviews.

Broad scans are visible Large numbers of SYN packets across many ports stand out clearly in packet captures.
Banners reveal context Service banners expose version and product clues that help analysts and attackers.
Legacy services raise risk Cleartext protocols and old services increase exposure, especially outside controlled labs.
Labs are not production Metasploitable-style services are expected in training environments but dangerous on real networks.
Nmap NSE leaves clues HTTP User-Agent values and request patterns can identify Nmap scripting activity.
Filters are tools Filters support investigation. They do not replace packet review or evidence-backed reasoning.
Patterns matter One packet rarely proves a full incident. Repeated behavior, context, and corroborating evidence matter.
Final report habit: Describe the Nmap case as reconnaissance and service enumeration unless additional evidence proves exploitation, data theft, malware, persistence, or compromise.
